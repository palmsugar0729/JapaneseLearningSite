## 2026-09-19（补记）— 匿名进度丢失修复 + 数据库备份上线

教科书词库部署上线、用户验收通过之后，当天追加的两件事。

### 一、匿名用户进度刷新即丢（既有缺陷，已修）

**现象**：不登录的学生背几个单词，一刷新进度全没。

**根因**：`App.vue` 只在有 token 时才调 `initSRSFromServer()` / `initExerciseFromServer()`，而这两个函数是唯一从 `localStorage` 读回进度的地方。匿名用户启动后 `progressMap` 始终为空，下一次 `saveAll()` 就用空 map 覆盖写回了 localStorage。**错题本和练习历史同样中招**——`useExerciseProgress` 是一模一样的写法。

**修法**：两个 init 都改成「先用 localStorage 垫底 → 有 token 再用服务端数据覆盖」，`App.vue` 去掉 `if (getToken())` 改为无条件调用。函数随之改名 `initSRS` / `initExercise`（不再只是「从服务器拿」）。

**⚠️ 一个必须记住的陷阱**：登录/注册成功后**不要**再调这两个函数。新账号服务端是空的，一调就把内存里匿名试用的进度覆盖掉了。现状恰好是「登录后不调用」，所以匿名进度会在下次 `saveAll()` 时随登录态一起推到服务端，等于天然继承。两个函数里都写了注释钉住这点。

**退出登录**：`App.vue` 和 `UserCenter.vue` 各有一份 `handleLogout`（重复实现），都补了「退出后重新 init 读回本机数据」——否则内存清空后用户随手一点，`saveAll()` 会把本地匿名进度冲掉。

**⚠️ 小程序端是反的**：`codes/miniprogram/src/pages/login/login.vue` 在登录后**会**调 init，所以小程序踩的是反向的坑（匿名进度被新账号覆盖）。小程序暂缓上线，本次未改动，恢复开发时要一并处理。

### 二、顺带修掉的鉴权漏洞

`/user` 路由漏了 `requiresAuth`，未登录能直接进用户中心（模板有 `isLoggedIn` 判断所以没崩，但与「未登录跳登录」不一致）。已补。

> `/privacy` `/contact` **必须保持公开**，备案要求，不能加 `requiresAuth`。

### 三、数据库备份（此前完全没做）

线上库此前**零备份**，且跑在 WAL 模式——主库文件只有 4KB，真实数据压在 190KB 的 `-wal` 里，直接 `cp` 拿到的是不完整快照。

新增 `server/scripts/backup-db.mjs`：在线备份 API → `integrity_check` 校验（**坏备份当场删掉并非零退出**，不留假备份）→ 转成非 WAL 单文件 → 轮转留 14 份。用 server 已有的 better-sqlite3，**不需要装 sqlite3 CLI**。

> 部署指南原来那条 `sqlite3 ... ".backup"` 命令**在服务器上根本跑不通**——服务器没装 `sqlite3` 这个命令。已更正为脚本做法。

crontab 每天 03:17，日志 `/var/log/jplearning-backup.log`。首次手动跑通：52KB 单文件 / 2 用户。

**验证**：本地拿「源库 vs 备份」逐行 sha256 比对，users 与 srs_progress 完全一致，确认备份**可用于还原**——而不只是 `integrity_check` 通过。

⚠️ **同盘备份防不了磁盘损坏**，只能防误删和写坏。异地容灾（COS 或本机拉取）尚未做。

### 二、关键决策：个人备案站点怎么写运营者

用户是**个人备案**，所以「主办单位名称」就是**真实姓名**，用户明确不愿公开。讨论后定的写法：

> 本站（jplearning.palmsugar.cn，以下简称「本站」）是一个由**个人开发者**运营的日语学习工具网站（**沪ICP备2026043380号-1**）。

**理由：** 隐私政策要满足的是「告知数据处理者是谁 + 怎么联系」，并不要求逐字照抄备案主体名称。**备案号本身就是指向官方登记主体的唯一标识** —— 任何人凭 `沪ICP备2026043380号-1` 都能在工信部备案系统查到真实主体，页面上还有联系邮箱，可追溯性完全成立。个人站点不写真名、改写成「个人开发者」是普遍做法。

> 补充事实：工信部备案查询系统对所有人开放，个人备案的「主办单位名称」一栏本就公开可查。所以如果那栏显示全名，真名其实早已公开，此改动主要是避免在页面上**主动**展示。

### 关于第 4 点：为什么不是单纯的「奶白色」

用 WCAG 公式把渐变两端都算了一遍（相对亮度 + 对比度）：

| 前景色 | 压在渐变上 | 压在深色底上 |
|--------|-----------|-------------|
| 原 `#999` | 1.46 ~ 1.86:1 ❌ | — |
| 奶白 `#f2f6f3` | **1.40 ~ 1.78:1** ❌ | **6.66 ~ 7.06:1** ✅ |
| 深色 `#2c3e50` | 5.64 ~ 7.18:1 ✅ | — |

关键结论：**本站底色是浅绿渐变，字越亮越糊** —— 直接换成奶白色（1.40~1.78:1）比原来的灰还要差。所以做法是在 footer 加一层半透明深色底（`rgba(44,62,80,.82)`，取自站内文字色 `#2c3e50`），奶白字压在这层底上是 **6.66~7.06:1**，达到 WCAG AA（正文 ≥ 4.5:1）。既拿到你要的奶白色观感，又真正可读。

> 备选方案：不加底色、把字改深色，也有 5.64~7.18:1。放弃它是因为你要的是奶白色调。

### 6.5 安全修复：轮换 `JWT_SECRET`

部署后核对环境变量时发现线上**从来没有 `.env`**（`package.json` 里也没有 `dotenv`），后端一直回退到 `server/src/auth.ts:4` 硬编码的 `'japanese-learning-dev-secret'`。而源码公开在 GitHub 上 —— **任何看过源码的人都能给任意 `userId` 签发合法 token，冒充任意用户登录**。这不是理论风险，是可复现的。

既然站点当前无人使用，当场把它换掉：

1. 服务器上 `openssl rand -hex 32` 生成 64 位密钥，写入 `/root/.jplearning-secrets.env`（`umask 077`，权限 600，属主 root）
2. `set -a; . 密钥文件; set +a` 后 `pm2 restart japanese-api --update-env` 注入进程环境
3. `pm2 save` 写进 dump —— **这步不能省**，否则主机重启（`pm2-root.service` 按 dump 恢复）会静默退回默认值，漏洞复活

**验证**（拿受鉴权保护的 `GET /api/progress/srs` 当探针，用 `jsonwebtoken` 现签 token 打线上）：

| 用哪把密钥签 token | 期望 | 实测 |
|-------------------|------|------|
| 旧默认值 `japanese-learning-dev-secret`（公开的） | 401 拒绝 | ✅ **401** |
| 密钥文件里的新值 | 200 放行 | ✅ **200** |
| 不带 token（基线） | 401 | ✅ 401 |

另确认 `/root/.pm2/dump.pm2` 中已含 64 位新密钥且与密钥文件一致、非默认值，`systemctl is-enabled pm2-root` 为 `enabled` —— **重启不会退回**。轮换使存量已登录用户掉线，因当前无人使用，无实际影响。

> 密钥值全程未回显到对话里，只核对长度与一致性。回滚方式是把 `JWT_SECRET` 从环境里去掉（旧值即源码默认值），但那等于恢复漏洞，仅用于临时排障。
